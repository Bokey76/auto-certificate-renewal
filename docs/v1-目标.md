# v1 目标说明

状态：待确认  
日期：2026-10-27  
修订：运行时改为 Node.js 24.22.1 及以上；密钥只放在不提交的 `.env`。第二期增加控制机和网页，第一期仍可单机运行。

本文是第一期的目标：做什么、不做什么、一条任务怎么跑。操作步骤见 [配置.md](配置.md)、[使用.md](使用.md)，模块与函数见 [源码.md](源码.md)。

## 目标

在多台 Linux 服务器上，用同一套镜像和各自的一份配置，完成 Let’s Encrypt 证书的签发、续签和应用。

一台机器上可以有多条任务。每条任务对应一张证书，证书上可以有多个域名（SAN，含泛域名）。任务按配置选择：

- 校验方式：HTTP-01 或 DNS-01（阿里云云解析）
- 应用到宝塔 Nginx、自装 Nginx、阿里云 CDN，或它们的组合
- 签发成功后执行一条自定义命令

某一条任务的配置不合法或执行失败时，其余任务继续执行。

## 已定决策

| 项 | 决定 |
| --- | --- |
| 运行方式 | Docker 镜像。编排层使用 Node.js 24，版本不低于 24.22.1。镜像内安装 Certbot，通过命令行调用 |
| 签发 | 每条任务单独调用一次 Certbot。任务 id 就是 Certbot 的证书名，重复运行续的是同一张证书 |
| 校验 | 按任务选择 HTTP-01 或 DNS-01。DNS-01 只对接阿里云云解析，使用官方 SDK `@alicloud/alidns20150109` |
| 阿里云 | 官方 SDK。证书上传到数字证书管理服务（`@alicloud/cas20200407` 的 `UploadUserCertificate`），再用 `@alicloud/cdn20180510` 的 `SetCdnDomainSSLCertificate` 绑定到 CDN 域名 |
| 加速产品 | 第一期只做 CDN 内容分发 |
| Nginx | 宝塔和自装是两种应用动作。替换证书文件，`nginx -t` 通过后再 reload。不改站点 server 配置，不写宝塔面板数据库 |
| 重载方式 | 容器使用 `pid: host` 和特权模式，用 `nsenter` 进入宿主机 mount 命名空间，执行宿主机上的 nginx 二进制 |
| 多机 | 第一期每台机器独立运行自己的配置。每次运行写下第二期控制机能汇总的状态 |
| 自定义 | 内置动作之外，每条任务可以有一条命令钩子 |
| 界面 | 第一期没有网页。第二期在控制机上查看各机状态、配置、日志、证书和 Nginx |

阿里云 Node SDK 与 Python SDK 同源，证书、CDN、云解析三个包都在持续发布。Docker 抹平了宿主机运行时差异，编排层用 Node.js。

Node.js 24.22.1 是 2026-10-21 发布的安全版本，修复了该系列上的高危问题，其中包括 Brotli 解码器越界写（CVE-2026-111497）和 TLS 主机名校验绕过。镜像基础使用官方 Node 24 镜像中不低于 24.22.1 的标签，例如 `node:24.22.1-bookworm`。同一条 24 线上更高的补丁版本可以替换。不使用 24.22.0 及更早的 24.x。

## 第一期要交付的

仓库落地时包含：

- 可构建的镜像（Node.js 24.22.1 或同一条线上的更高版本、Certbot、`nsenter`）
- `docker-compose.yml` 示例
- `config/config.example.yaml`
- `.env.example` 与 `.gitignore`。`.env` 不进入仓库
- 命令 `cert-renew run`、`cert-renew run --job <id>`、`cert-renew run --dry-run`

操作者准备好配置、环境变量和目录挂载后，`docker compose up -d` 即可按时刻表续签。

## 第一期不做

- 不做 ACME 协议本身，签发全部交给 Certbot
- 不扫描宝塔数据库，不自动发现站点
- 不修改 Nginx 的 server 配置（HTTP-01 所需的 location 由操作者按下面的片段加好）
- 不回写宝塔面板里显示的证书记录
- 不做 DCDN、ESA，以及其他云厂商
- DNS-01 不接阿里云以外的解析商
- 不在机器之间拷贝证书。多台源站要使用同一张证书时，第一期没有「只应用、不签发」的角色
- 不删除数字证书管理服务里的旧证书
- 第一期不做网页、控制机和通知渠道。状态与日志按第二期能汇总的方式记录
- 任务串行执行，第一期不并行

## 一条任务怎么跑

任务按配置文件中的顺序逐条执行。单条步骤：

1. 校验这条任务的字段。字段不合法则记录失败，进入下一条。
2. 读取状态文件和当前证书到期时间。
3. 证书剩余时间多于 `renewBeforeDays`（默认 30 天），并且没有失败待重试的应用动作：记为跳过，不调用 Certbot，不跑钩子。
4. 证书缺失、落在续签窗口内，或上次签发失败：调用 Certbot。失败则记录，不执行应用动作，也不跑钩子，进入下一条。
5. 证书已经在数据卷里，但某些应用动作上次失败：跳过 Certbot，只重试失败的动作。
6. 按配置顺序执行应用动作。一个动作失败，同任务里后面的动作继续执行。
7. 仅当这一轮 Certbot 实际签发出新证书时，才执行钩子。钩子失败记入本任务，不回滚已经完成的 Nginx 或 CDN 更新。
8. 把证书指纹、每个动作的成败、CDN 使用的证书 ID 写入状态文件。

整份 YAML 无法解析，或根字段不合法时，进程不知道哪些任务可以跑，以退出码 1 结束，不执行任何任务。

退出码：

| 码 | 含义 |
| --- | --- |
| 0 | 全部任务成功或被跳过 |
| 1 | 配置文件无法读取，或根结构不合法 |
| 2 | 已执行，至少一条任务失败 |

标准输出按行写日志，每行带时间和任务 id。结束时打印一行汇总：总数、跳过、成功、失败。

## 配置

配置文件固定为容器内 `/config/config.yaml`，可用环境变量 `CONFIG_PATH` 改路径。编码 UTF-8，格式 YAML。域名、证书路径、任务开关写在 YAML 里。仓库模板是 `config/config.example.yaml`，复制为同目录的 `config.yaml` 后由 compose 挂进容器。

本仓库是公开仓库。AccessKey、AccessKey Secret 以及其他凭据只放在项目根目录的 `.env`。`.env` 被 `.gitignore` 排除，不提交。仓库里提交 `.env.example`，只列出字段名和空值。容器通过 compose 的 `env_file` 读取 `.env`。已提交的 compose 文件里不出现密钥。

默认读取：

- `ALIBABA_CLOUD_ACCESS_KEY_ID`
- `ALIBABA_CLOUD_ACCESS_KEY_SECRET`

任务上的 `credential` 可改用另一组变量：`ALIBABA_CLOUD_ACCESS_KEY_ID_<NAME>` 与 `ALIBABA_CLOUD_ACCESS_KEY_SECRET_<NAME>`。`credential: prod` 对应后缀 `_PROD`。这组变量同样只写在 `.env`。`TZ` 也放在 `.env`。

```yaml
serverName: origin-a          # 可选。第二期控制机用来识别这台机器

letsencrypt:
  email: ops@example.com
  staging: false
  renewBeforeDays: 30
  keyType: ecdsa          # ecdsa（P-256）或 rsa（2048）

alibaba:
  regionId: cn-hangzhou

schedule:
  hours: [3, 15]          # 可选。时区内每天检查的小时，默认 3 和 15

jobs:
  - id: www-example
    enabled: true
    domains:
      - example.com
      - www.example.com
    challenge:
      type: dns-01
      zone: example.com
      propagationSeconds: 60
    apply:
      - type: nginx
        kind: baota
        certDir: /www/server/panel/vhost/cert/example.com
      - type: aliyun-cdn
        domainNames:
          - example.com
          - www.example.com
    hook:
      command: /hooks/after-issue.sh
      timeoutSeconds: 60

  - id: origin-api
    domains:
      - api.example.com
    challenge:
      type: http-01
      webroot: /var/www/acme
    apply:
      - type: nginx
        kind: custom
        fullchainPath: /etc/nginx/ssl/api.example.com/fullchain.pem
        privkeyPath: /etc/nginx/ssl/api.example.com/privkey.pem
        nginxBin: /usr/sbin/nginx
```

字段约定：

- `jobs[].id`：同一文件内唯一。字符为小写字母、数字、连字符，长度 1–40，且不能以连字符开头或结尾。它同时作为 Certbot 证书名和状态文件名。
- `domains`：至少一个。允许 `*.example.com`。出现泛域名时，校验方式必须是 `dns-01`。
- `challenge.type`：`http-01` 或 `dns-01`。
- `dns-01.zone`：阿里云解析里的主域名，必填。程序用它定位 TXT 记录，不自行猜测根域。
- `http-01.webroot`：默认 `/var/www/acme`。
- `keyType`：默认 `ecdsa`。
- `staging: true` 时使用 Let’s Encrypt 的测试环境，证书不受浏览器信任。
- `enabled: false` 的任务记为跳过。
- 应用动作和钩子都可以不写。都没有时，证书只保存在数据卷里。

`cert-renew run --dry-run` 只做 Certbot 演练：不替换 Nginx 文件，不调用阿里云，不执行钩子。

## 校验

### HTTP-01

使用 Certbot 的 webroot 模式。容器把校验文件写到 `webroot`，由宿主机上已经在跑的 Nginx 对外提供。容器不占用 80 端口。

每个走 HTTP-01 的站点，需要能用 HTTP 访问到校验路径。下面这段要放在会把 HTTP 重定向到 HTTPS 的规则之前：

```nginx
location ^~ /.well-known/acme-challenge/ {
    default_type text/plain;
    alias /var/www/acme/;
}
```

宝塔会重写站点主配置。这段放到面板的扩展目录，避免被覆盖，例如：

`/www/server/panel/vhost/nginx/extension/<域名>/acme.conf`

`alias` 的目录必须和本条任务的 `webroot` 是同一宿主机目录，并挂进容器。

### DNS-01

Certbot 使用 `manual` 校验。镜像提供 auth hook 和 cleanup hook，由 Node 调用阿里云云解析：

- 新增 TXT：主机记录由域名和 `zone` 算出。`example.com` 对应 `_acme-challenge`，`www.example.com` 且 zone 为 `example.com` 时对应 `_acme-challenge.www`
- 等待 `propagationSeconds`（默认 60）秒后再让 Certbot 继续
- 同一主机记录上可能有多条 TXT。一张证书同时包含 `example.com` 和 `*.example.com` 时会出现这种情况，必须都加上
- 清理时只删除这一轮自己创建的记录

这一轮用到的云解析权限：添加记录、删除记录、按条件查询记录。

## 应用到 Nginx

两种 `kind` 都只替换已经在使用的证书文件。站点配置里的证书路径由操作者事先写好。

| | `baota` | `custom` |
| --- | --- | --- |
| 证书位置 | `certDir` 下的 `fullchain.pem` 与 `privkey.pem` | `fullchainPath` 与 `privkeyPath` |
| nginx 二进制 | 默认 `/www/server/nginx/sbin/nginx`，可用 `nginxBin` 覆盖 | `nginxBin` 必填 |
| 常见证书目录 | `/www/server/panel/vhost/cert/<名称>/` | 由配置指定 |

写入规则：

1. 目标目录不存在则创建。
2. 已有文件先备份到同目录的临时文件。
3. 写入新的 fullchain 与 privkey。私钥权限 `600`，证书权限 `644`，属主 root。
4. 用 `nsenter` 在宿主机 mount 命名空间执行 `<nginxBin> -t`。
5. 测试失败：还原备份，不 reload，该动作失败。
6. 测试成功：执行 `<nginxBin> -s reload`。reload 失败则还原备份，再 reload 一次以回到旧证书，该动作失败。
7. reload 成功后删除备份。

宝塔 Nginx 依赖宿主机上的动态库。执行前先进入宿主机 mount 命名空间，再调用宿主机上的 nginx 二进制。

一个动作的测试或 reload 失败，不影响同任务里其余动作，包括阿里云 CDN。

## 应用到阿里云 CDN

前置条件：CDN 上该域名已经存在，并且开通了 HTTPS 加速。程序不去创建 CDN 域名。

一轮签发对应一次上传：

1. 确认每个 `domainNames` 都被本证书覆盖（完整域名相等，或被本证书里的泛域名覆盖）。有任何一个不符合，整个 CDN 动作失败，不上传。
2. 调用 `UploadUserCertificate`。证书名称形如 `acme-<任务id>-<YYYYMMDD>`，最长 63 个字符；重名时追加 `-2`、`-3`。每次新签发都上传一张新证书。
3. 对每个加速域名调用 `SetCdnDomainSSLCertificate`：`CertType=cas`，`CertId` 为上一步返回的 ID，`SSLProtocol=on`。域名之间互不影响。
4. 状态里记下证书指纹、CertId 和每个域名的成败。

下一轮如果证书没变、只是某个域名上次绑定失败：不再上传，用已保存的 CertId 重试那些失败域名。

上传用到的权限是 `yundun-cert:UploadUserCertificate`，绑定用到的权限是 `cdn:SetCdnDomainSSLCertificate`。

旧证书留在数字证书管理服务里，第一期不自动清理。

## 钩子

`hook.command` 在容器内执行，默认超时 60 秒，上限 300 秒。非 0 退出码或超时都算该任务失败。

仅在这一轮 Certbot 实际写出新证书时执行。因为未到期而跳过、或只是重试上次失败的 CDN / Nginx 时，不执行钩子。

钩子进程的环境变量：

| 变量 | 内容 |
| --- | --- |
| `CERT_JOB_ID` | 任务 id |
| `CERT_DOMAINS` | 逗号分隔的域名 |
| `CERT_LIVE_DIR` | 数据卷中该证书的 live 目录 |
| `CERT_FULLCHAIN` | live 目录里的 fullchain.pem |
| `CERT_PRIVKEY` | live 目录里的 privkey.pem |
| `CERT_NOT_AFTER` | 到期时间，ISO 8601 |

钩子与编排进程权限相同，可以进入宿主机命名空间。配置由机器管理员编写。

## 状态

数据卷挂在容器内 `/var/lib/acme`：

- Certbot 的账户、证书和续签配置
- `state/<任务id>.json`：指纹、到期时间、各动作结果、CDN CertId、钩子已针对哪次指纹执行过

动作的状态键必须稳定，不随配置里的数组下标变化：

- Nginx：目标证书文件路径
- CDN：加速域名
- 钩子：固定键 `hook`

丢失这个数据卷会丢掉 Let’s Encrypt 账户和本地证书，下一次会重新注册并重新签发，有机会撞上颁发配额。数据卷需要纳入机器备份。

Let’s Encrypt 对每个注册域名有每周签发数量限制。稳定的任务 id、未进入续签窗口就不签发、联调使用 `staging: true`，是避开配额的办法。

## Docker 部署

镜像基于 Debian Bookworm 的官方 Node.js 24 镜像，Node 版本不低于 24.22.1，并安装 Certbot 与 `nsenter`。

目标形态的 compose：

```yaml
services:
  renew:
    image: auto-certificate-renewal:local
    build: .
    command: ["cert-renew", "schedule"]
    pid: host
    privileged: true
    env_file:
      - .env
    volumes:
      - ./config/config.yaml:/config/config.yaml:ro
      - acme-data:/var/lib/acme
      - /www/server/panel/vhost/cert:/www/server/panel/vhost/cert
      - /var/www/acme:/var/www/acme
    restart: unless-stopped

volumes:
  acme-data:
```

挂载按这台机器真正要写的目录增减。只做 DNS-01 和 CDN、本机没有 Nginx 时，可以不挂证书目录和 webroot。

手动跑：

```bash
docker compose run --rm --entrypoint cert-renew renew run
docker compose run --rm --entrypoint cert-renew renew run --job www-example
docker compose run --rm --entrypoint cert-renew renew run --dry-run
```

时刻表：时区取 `TZ`，默认 `Asia/Shanghai`。每天在配置的 `schedule.hours`（默认 03:00 和 15:00）附近运行。每次睡前随机 0–30 分钟偏移，不持久化，使多台机器错开。容器每次启动先执行一轮，再进入时刻表。证书未到期时，多跑一轮只会跳过签发。

HTTP-01 和 DNS-01 都不需要 `network_mode: host`。容器只需要出站访问 Let’s Encrypt 和阿里云 API。80 端口仍由宿主机 Nginx 占用。

特权模式和 `pid: host` 是为了 `nsenter` 能调用宿主机 nginx。容器内的进程因此具备进入宿主机命名空间的能力。镜像和配置按主机 root 级别的权限来对待。

## 多台机器

第一期每台机器使用同一镜像、自己的 `config.yaml`、自己的 `acme-data` 卷，以及自己的目录挂载。控制机不在线时，本机仍按本地配置续签。

同一域名只在一台机器的配置里签发。CDN 和源站 Nginx 如果都由这台机器负责，写在同一条任务的 `apply` 里。

每次运行除了 `state/<任务id>.json`，还要留下一份给第二期控制机读取的汇总，放在数据卷的 `status.json`。里面至少有：

- 本机标识。第一期用配置里的 `serverName`，缺省时用主机名
- 最近一轮的开始时间、结束时间、退出码
- 每条任务的结果：成功、跳过或失败，失败原因，证书到期时间
- 每个 Nginx 动作的 `nginx -t` 与 reload 结果
- 最近一轮日志的路径

`serverName` 写在配置根上，可选。

## 第二期：控制机和网页

第二期加一台控制机，管理多台已经装好本程序的机器。第一期不实现控制机和网页，但上面的 `status.json` 就是它的数据来源。

控制机提供网页，用来：

- 看到每台机器是否在线、最近一轮何时跑完、退出码是什么
- 看到每张证书的域名、到期时间、签发结果、CDN 是否绑定成功
- 看到每台机器上 Nginx 动作的测试和 reload 结果
- 查看、修改下发到各机的任务配置
- 查看每台机器的运行日志

各机仍由本机容器执行 `nginx -t` 和 reload。控制机不进入其他机器的命名空间。配置下发和日志查看的具体协议到第二期再定。控制机停机时，各机继续按上一份本地配置工作。

## 验收

下面每条都要能在测试环境（`staging: true` 或 `--dry-run`，外加一个真实的阿里云测试域名，如果要验 CDN）观察到：

1. 一份配置里有两条合法任务和一条字段不合法的任务。不合法的那条失败，另外两条仍完成签发和应用。
2. HTTP-01 与 DNS-01 各至少一条任务能签发测试证书。泛域名任务走 DNS-01。
3. `nginx -t` 失败时，正在运行的 Nginx 不被 reload，备份被还原；同任务的 CDN 动作仍会执行。
4. CDN 动作上传证书并拿到 CertId，再对配置中的每个加速域名开启 HTTPS。其中一个域名绑定失败时，另一个域名仍可成功。
5. 证书剩余时间多于续签窗口时，再次运行不调用 Certbot。
6. 证书未变、CDN 绑定曾经失败时，再次运行只重试绑定，不重新签发，也不重新上传。
7. 钩子只在实际签发成功后执行，跳过和单纯重试都不执行。钩子返回非 0 时该任务失败，已 reload 的 Nginx 保持新证书。
8. 两台机器使用同一镜像、不同配置，各自只处理自己的任务。每台数据卷里有 `status.json`，能看出本机任务结果、证书到期时间和 Nginx 动作结果。
